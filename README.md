# goit-algo-hw-05

Порівняння трьох алгоритмів пошуку підрядка — Boyer-Moore, Knuth-Morris-Pratt
та Rabin-Karp — на двох україномовних текстах.

## Структура

- `algorithms.py` — реалізації трьох алгоритмів з нуля + два C-baselines зі stdlib (`str.find`, `re.search`).
- `benchmark.py` — завантажує статті, перевіряє коректність, міряє час через `timeit`, малює графік.
- `article_1.txt`, `article_2.txt` — тестові тексти (наукові статті з посилань завдання).
- `benchmark.png` — графік результатів (генерується скриптом).

## Залежності

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install matplotlib
```

## Запуск

```bash
python3 benchmark.py
```

Скрипт спочатку перевіряє що всі три алгоритми дають однаковий
результат (sanity check), а потім міряє час по 200 запусків
на кожну комбінацію `(стаття × тип паттерну × алгоритм)`.

## Результати (приклад прогону, мс на запуск)

Власні Python-реалізації — перші три колонки. `str.find()` і `re.search()` —
нативні C-baselines зі stdlib, для контексту.

| article   | pattern  | Boyer-Moore | KMP    | Rabin-Karp | str.find()  | re.search() | winner       |
|-----------|----------|-------------|--------|------------|-------------|-------------|--------------|
| article 1 | existing |   0.007     | 0.015  | 0.049      |  **0.0001** | 0.001       | str.find()   |
| article 1 | missing  |   0.114     | 0.873  | 2.849      |  **0.001**  | 0.007       | str.find()   |
| article 2 | existing |   0.002     | 0.006  | 0.013      |  **0.0001** | 0.001       | str.find()   |
| article 2 | missing  |   0.165     | 1.273  | 4.264      |  **0.002**  | 0.010       | str.find()   |

Серед **власних реалізацій** переможець у всіх 4 випадках — **Boyer-Moore**.
Серед усіх — нативний `str.find()` бʼє всіх з відривом у 80-150×.

Графік: `benchmark.png` (лог-шкала, інакше Python-стовпчики на 2-3 порядки
вище за C-baselines і їх не видно одночасно).

## Висновки

**Boyer-Moore виграв у всіх чотирьох замірах**, причому у випадку
`missing`-паттерну розрив особливо великий — він у 9–10 разів швидший
за KMP і у 25–27 разів швидший за Rabin-Karp.

### Чому так

**Boyer-Moore** виграє завдяки евристиці «поганого символа». На
кожній невдалій спробі він може зсунути паттерн одразу на кілька
позицій (іноді на всю його довжину). Для вигаданого паттерну, якого
немає в тексті, символи майже завжди «погані», тому BM просто
пролітає по тексту великими кроками. Для існуючого — він знаходить
збіг швидко й виходить.

**KMP** теж лінійний за часом, але робить рівно один прохід по
тексту без можливості великих стрибків. Префікс-функція допомагає
не повертатися по тексту, проте кожна позиція все одно перевіряється.
Тому на `missing` KMP мусить пройти весь текст до кінця, що видно
у різниці часу existing/missing — ~60× у статті 1 і ~220× у статті 2.

**Rabin-Karp** у цій реалізації найповільніший. Причина проста:
для кожної позиції тексту він рахує хеш поточного "вікна" і робить
кілька арифметичних операцій (`*`, `%`, `ord()`). У Python кожна така
операція виконується повільно, бо інтерпретатор робить багато додаткової
роботи для кожного кроку (на відміну від C, де це просто кілька
машинних інструкцій). На C RK був би конкурентоспроможним, але у pure
Python він програє і BM, і KMP.

### По статтях

- **Стаття 1** (~21 KB): найшвидший — **Boyer-Moore** на обох паттернах.
- **Стаття 2** (~32 KB): найшвидший — **Boyer-Moore** на обох паттернах.

### Загальний висновок

Boyer-Moore — оптимальний вибір **серед власних реалізацій** для пошуку
підрядка у текстах природною мовою, особливо коли паттерн ймовірно
відсутній: великий алфавіт (українська + латиниця + цифри + пунктуація)
дає bad-character евристиці максимальну ефективність, а ранній вихід при
першому збігу робить його швидким і для existing-паттернів.

KMP — гарна теоретична гарантія `O(n + m)` без залежності від
алфавіту, але на практиці для довільних текстів BM швидший.

Rabin-Karp у pure Python — не варіант для одиничного пошуку.
Він свою нішу займає там, де потрібно шукати багато паттернів одночасно
або у задачах виявлення плагіату (порівняння хешів багатьох
підпослідовностей), а не для класичного `find one in many`.

### А що ж нативні baselines?

`str.find()` в CPython реалізований на C і випереджає наш Boyer-Moore у
80-150 разів. Це нагадування, чому в продакшені ніхто не пише власне
сортування чи пошук підрядка: навіть теоретично оптимальний алгоритм у
Python програє індустріальному C-коду, бо у Python кожен крок (взяти
символ, порівняти, інкрементувати індекс) виконується інтерпретатором
поетапно, а в C це декілька машинних інструкцій, які виконуються
напряму процесором за наносекунди.

`re.search()` повільніший за `str.find()` у 5-10 разів. Це теж C-код, але
регулярки роблять додаткову роботу: спочатку треба розібрати паттерн
(навіть якщо він простий, без спецсимволів), а потім запустити загальний
матчер регулярних виразів. `str.find()` спрощений до конкретної задачі
пошуку підрядка і тому швидший.

Власні реалізації Boyer-Moore / KMP / Rabin-Karp залишаються корисними
**як навчальний матеріал** — для розуміння *чому* і *як* саме `str.find()`
такий швидкий. У реальному коді — `text.find(pattern)`, і не вигадуйте велосипед.
